# 指定应用残留检查：建议、设计与实施计划

日期：2026-10-30。基线：当前工作区与文档标注的 0.9.8。状态：2026-10-30根据审阅收敛首期范围，设计待实施，没有新增产品能力。本轮只编写文档，不升级、构建或交付应用。

## 1. 目标与判断思路

用户希望检查类似 CC Switch 卸载后的残留。核心问题不是文件是否占用空间，而是：哪些文件可能属于该应用、依据是什么、应用是否仍在使用、哪些范围没有检查。

推荐先交付“指定应用的只读残留检查”，从 CC Switch 做第一个有证据的样例。不以目录名相似、应用目录不存在或进程未运行推断可删除；归属判断与安全删除判断分开。

思路顺序：确认应用身份 → 确定有限检查范围 → 收集只读证据 → 列出关联候选及不确定性 → 报告覆盖缺口。未来清理必须另做计划、复核和明确确认，不能复用一次扫描授权。

## 2. 已确认现状

依据：当前 `src-tauri/src/core.rs` 的固定规则、主要目录和 `excluded_app_data`，以及 [能力差距清单](../capability-matrix.md)、[项目说明](../../README.md)。本轮为源码检查，未运行应用实测。

| 本次案例 | 当前能力 | 缺口 |
| --- | --- | --- |
| `~/Downloads/CC-Switch-v4.0.21-macOS.dmg` | 下载目录可只读分析、浏览 | 不关联应用身份，不判断残留 |
| `~/.cc-switch` | 主目录扩展扫描可观测，受预算和权限限制 | 无专属识别、敏感配置分类及归属解释 |
| `~/Library/Application Support/CrashReporter/cc-switch_*.plist` | Application Support 被主动排除 | 普通扫描不会检查该位置 |
| `/Volumes/CC Switch/CC Switch.app` | `/Volumes` 不在八个主要根中 | 无安装镜像与应用关联检查 |
| 应用、进程及安装记录 | 没有统一应用残留报告 | 无法回答是否已卸载干净 |

本次会话曾发现挂载镜像中的 CC Switch 4.0.21，应用标识为 `com.ccswitch.desktop`，未在常规应用目录找到副本或发现运行进程。上述配置、安装包和崩溃记录随后已由用户授权清理，镜像已推出。这是单机样例，不能证明所有版本均使用相同路径；不能再用已删除的真实数据宣称扫描验收通过。

## 3. 两种方案与推荐顺序

| 方案 | 适用场景 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A：指定应用只读检查，推荐首期 | 用户明确要检查一个应用 | 范围可控，易解释，能针对案例验收 | 仅支持有依据的规则；未知应用只能显示有限候选 |
| B：完整应用与关联数据账本 | 批量应用管理、后续卸载 | 统一应用列表、关联及共享数据视图 | 涉及更多归属、安装渠道、权限和生命周期判断 |

先实施 A；B 作为后续专项，不加入首期。KISS：围绕一次指定应用检查；YAGNI：不做全盘自动发现、规则插件和通用删除；DRY：复用覆盖诊断、预算、取消与展示组件；SOLID：应用身份和关联判定独立于通用空间扫描及执行清理。

## 4. 首期范围与交互

入口暂定“应用残留检查”，首期只提供 CC Switch 固定预设，不提供名称／Bundle ID 自由输入或未知应用搜索。预设标识 `com.ccswitch.desktop` 与路径来源按本机4.0.21历史样例标注，不宣称覆盖其他版本。通用应用输入和完整应用账本后续另行设计。

首期采集仅含三个来源：`~/.cc-switch`配置目录元数据、`~/Downloads`第一层名称线索、`~/Library/Application Support/CrashReporter`第一层名称线索。下载候选仅接受不区分大小写的精确模式`CC-Switch-v<数字版本>-macOS.dmg`（版本由数字和点组成且不能为空、不能连续点）；崩溃记录仅接受`cc-switch_`前缀且`.plist`后缀，均为弱线索，不靠去符号匹配提升归属强度。专属目录为历史样例关联，不是独占或可删除证明。

首期不查应用副本、进程、安装收据或挂载镜像，不读取Info.plist。报告中这些来源明确标记“未纳入本次检查”，应用是否安装及是否活动均为“未知／未检查”。不得因为配置目录不存在就判断应用已卸载。以上收敛约定优先于下文保留的后续设计线索。

扫描前列明将检查的位置及敏感范围，用户主动启动后进行有限只读检查。结果呈现：预设身份及历史来源、活动状态未知、关联候选、分来源覆盖和错误。操作仅允许重新检查、展开依据及经路径复核的 Finder 定位。

首期不提供删除、移入废纸篓、推出卷、结束进程、挂载安装包、读取钥匙串或修改权限。不读取配置正文、令牌、会话、数据库及崩溃报告正文。首期不读取应用包正文；将来增加应用副本发现时，才允许有界读取Info.plist必要字段并另行验收。

不得显示“已完全卸载”“所有候选均可清理”。结果文案使用“本次检查范围内未发现候选”；遗漏、拒绝、超限和取消均单列。

## 5. 识别与覆盖边界

### 首期实现契约（优先执行）

**请求与任务：** 只接受固定预设ID `cc-switch`，其他值在开始任务及访问文件前拒绝。沿用Engine任务互斥和取消，每次显式扫描才创建报告；页面导航、筛选和定位不重扫。报告仅内存保存，不新增持久化。

**分来源覆盖：** 每个来源独立返回ID、固定检查路径、检查方式、Coverage、问题计数和候选数。必须区分complete、absent、denied、failed、limited、cancelled、pending；候选为空不能替代状态。目录未发现仅对该固定来源成立。应用发现／进程／收据／挂载关联单列“未纳入”，不能用absent表示。汇总展示各状态数量，不以单一complete掩盖未纳入或部分来源。

**专项读取：** 新增窄接口仅接受内部枚举来源，不接收前端路径。CrashReporter只能在固定父目录枚举第一层元数据，不进入其他Application Support路径，不调用会递归或全局放宽`excluded_app_data`的参数。配置目录允许有界递归元数据统计；Downloads与CrashReporter只做第一层枚举，不递归候选目录。逐级拒绝符号链接，校验条目身份；缺失、拒绝、变化分别记录。读取异常不得跳过后标complete。既有通用扫描排除和删除Action不修改。

**统一预算：** 整个作业共用30秒截止时间、20,000条枚举预算和200候选上限；配置递归深度最多12层。来源之间不重置预算；未开始来源标pending并注明预算或取消原因。文件系统调用可能阻塞，30秒是协作检查预算而非硬实时保证。分配块、逻辑大小分字段，未知为null；不跨来源累加，不把硬链接／APFS共享空间当独占可回收量。

**候选定位：** 候选返回不可由路径替代的ID，后端报告保存对应路径、dev／inode／类型、观测时间，前端仅提交报告ID和候选ID。报告最多保留最近一份，有效期5分钟；重扫使旧报告失效。定位前重新校验固定来源包含关系、逐级无链接、文件身份及当前类型；消失／替换／过期时拒绝并提示重查。仅执行固定`/usr/bin/open`参数数组`-R`及复核路径，不拼接shell。不复用普通扫描的根ID或允许前端直接传路径。定位能力独立于删除能力。

**证据字段：** 每候选包含来源、规则ID／版本、匹配条件、历史样例依据、关联强度（样例路径／弱名称线索）、敏感性、观测统计和Coverage。统一`cleanupEligible=false`，配置明确标记可能包含凭据；正文不会返回前端。错误与路径以文本展示，诊断遵循现有条数／长度界限，不输出进程参数或正文。

### 应用身份

优先使用应用包中的 Bundle ID（应用标识）与显示名称；应用已不存在时，使用用户提供标识或内置已验证规则，并显示来源。应用名、文件名和标识之间不能靠统一去符号或模糊前缀直接建立强关联。

常规应用目录检查 `/Applications` 与 `~/Applications` 的有界应用发现；其他位置或便携安装未覆盖时必须说明。进程查询仅作活动线索，查询失败为未知，未发现进程不代表没有依赖。包安装收据也不能单独证明应用存在或已经卸载。

### 候选与证据

- 精确应用标识路径：明确记录匹配字段和来源，仍不等于可删除。
- 已验证专属路径：例如 CC Switch 的 `~/.cc-switch`，标记“配置／可能含凭据”，只统计元数据；保留验证版本与来源。
- 名称匹配：下载文件、镜像名、崩溃记录前缀只能作为弱线索；同名与近似名必须保留歧义。
- 共享或归属不明：显示原因，不推断独占，不纳入可回收量。

每条候选包含路径、类别、规则编号、匹配依据、证据来源、敏感性、观测占用与覆盖状态。关联强度和处理安全性分字段，不使用没有依据的置信百分比。

### 路径和系统边界

普通扫描的 `excluded_app_data` 保护保持有效。专项若要检查 CrashReporter，只能通过明确的固定父目录和有限枚举能力实现，不能关闭 Application Support 的全局排除或遍历全部私有数据。扫描前解释这一新增范围；系统拒绝时记录拒绝，不绕过隐私保护。

下载目录只枚举有限文件元数据，不挂载 DMG。已挂载镜像通过系统只读挂载信息建立设备、挂载点与镜像源线索；关联失败保留未知，不仅凭卷名宣称属于应用。外置卷及无关挂载卷不递归扫描。

输入长度、格式和路径均需验证。系统命令使用固定可执行文件和参数数组，不拼接 shell；查询设置超时并解析结构化输出，错误保留但不暴露敏感进程参数。

遍历不跟随符号链接、不跨设备；遇到消失或变化的文件记录状态。初始建议总预算 30 秒、候选最多 200 条、枚举条目最多 20,000 条、应用包标识文件最多 1 MiB，实施时通过样例调整并记录。达到任一限制返回部分结果，不宣称完整。容量仅为观测值，不计入可回收空间；重叠目录与硬链接复用已有去重语义，并说明 APFS 共享限制。

## 7. 分阶段实施与验收

### R1：规则与后端只读报告

1. 复核当前调用关系和专项访问边界，固定 CC Switch 样例与未知应用行为。
2. 创建临时目录fixture，覆盖三个首期来源存在／不存在、精确匹配／同名假阳性、配置元数据、崩溃记录和DMG名称；应用／进程／收据／挂载明确未纳入。
3. 实现纯匹配与受限采集；文件根和预算通过模块内部测试入口替换，不向IPC暴露任意根，不依赖当前机器仍安装CC Switch。
4. 验证来源白名单、符号链接、路径逃逸、拒绝／失败分类、超时／取消、共享预算、深度上限、文件消失和敏感正文不被读取；定位增加未知ID、旧报告、过期、同路径替换和链接替换拒绝测试。

完成标准：候选均有依据；未知状态不伪装为不存在；配置不标为可删除；普通扫描保护未被放宽。

### R2：界面与交互

1. 接通只读入口、范围确认、报告、候选详情和重新检查。
2. 模拟空结果、分来源缺失／拒绝／超限／失败／未访问、活动未知和共享不确定性；未知预设在后端拒绝，不显示未知应用已检查。
3. 验证页面切换、展开和筛选不触发删除、进程终止或挂载操作；并发扫描沿用任务互斥。
4. 检查键盘可达、中文错误提示和窄窗口布局；路径按文本显示。

完成标准：用户能回答“发现什么、凭什么关联、哪些没查到”，不存在清理按钮或默认选中。

### R3：真实只读验收及交付

使用临时样例和用户明确指定的真实应用进行只读验证；不要为复现而重建真实凭据、安装应用或制造系统残留。macOS 真实应用内分别验证允许、拒绝、取消和部分结果，终端扫描或模拟 IPC 不能代替应用权限验收。

运行相关 Rust 测试、前端构建与 UI 回归；共享扫描或边界发生变动时补既有清理保护测试。记录实际命令和结果。需要交付时按项目签名、版本同步和原生验收流程执行；权限未验收不得标为完成。

### R4：后续独立决策

只读能力验收后，再评估应用副本发现、Info.plist身份、进程活动、挂载关联及完整应用账本；这些不属于本轮R1～R3。之后才评估清理专项。清理必须另行定义共享资料保护、凭据和配置保留、执行前重新核验、逐项确认、失败中止及结果复查。安装镜像推出与文件移除也分别设计，不能由“疑似残留”一键推导。
