# 应用包签名修复计划

证据：0.8.3 实机仍出现文稿目录授权提示；当前交付包 codesign --verify --deep --strict 失败，只有 linker ad-hoc 可执行文件签名，Info.plist 未绑定，资源未封装。截图不能确定完全磁盘访问是否开启或具体弹窗归因。

方案一（当前采用）：配置 Tauri 完整 ad-hoc 应用包签名，修复当前同版本包，并增加交付校验。方案二（长期）：正式 Developer ID 签名及公证，需要开发者证书与账户，本轮不创建证书或改动钥匙串。

遵循 KISS/YAGNI：保留 0.8.3 和原扫描边界，不继续排除文稿，不重编译无改动业务代码。DRY：Tauri 标准 signingIdentity 配置负责未来打包；校验脚本统一版本、包标识和完整签名要求。

1. src-tauri/tauri.conf.json 的 bundle.macOS.signingIdentity 设置为 -。
2. 新增 scripts/verify-macos-bundle.py，只读验证完整应用签名、资源封装、版本与包标识，不修改或自动授予系统权限。
3. 当前包复制到临时位置后完整签名，验证通过才替换 release/留白.app；备份原包为 release/留白-0.8.3-签名前.app。
4. 正向验证修复包；负向验证旧包、资源篡改和清单篡改均失败。不自动启动第二份实例，避免与旧扫描混淆。
5. 更新验收文档：新签名仍需用户退出所有实例后重新添加授权，不声称文稿弹窗已解决；未来正式分发须采用稳定 Developer ID。

签名不代表系统授权。ad-hoc 构建身份可能在更新后变化；完全磁盘访问必须由用户操作，不重置 TCC，不自动点击允许。
