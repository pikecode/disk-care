# 分支、提交与版本管理

适用本仓库。目标是让源码、交付版本与验证记录相互对应；不采用长期`develop`分支，也不为每个版本建立长期分支。

## 分支职责

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 可追溯的本地交付基线 | 不直接开发功能；记录已完成检查与仍待验的边界，不等于已公证或对外正式发布 |
| `feat/<主题>` | 新功能与交互 | 从干净的`main`创建；一个分支只完成一个明确工作包 |
| `fix/<主题>` | 缺陷修复 | 写明触发条件与回归验证，复用原保护边界 |
| `docs/<主题>` | 仅文档 | 不为文档升级应用或运行不相关构建 |
| `chore/<主题>` | 工具、验证、版本整理 | 与产品改动区分；E5当前使用`chore/e5-native-validation` |

主题使用简短英文小写与连字符。已存在分支先检查其用途，不覆盖或重建。同一分支跨轮开发时，每轮仍增加修改记录；未完成工作不长期堆在未提交的工作区。

## 开始与提交

1. 读取`AGENTS.md`、总进度、最新修改记录及当前工作包，检查`git status --short`和当前分支。已有改动先确认归属，保留用户改动；不得用重置、清理、覆盖或自动暂存来强行获得干净目录。
2. 工作区干净时，从`main`创建短期分支。例如：

   ```bash
   git switch main
   git switch -c feat/application-details
   ```

3. 每个逻辑改动同时更新`docs/change-log.md`；提交说明采用`类型: 中文说明`，例如`fix: 修复无关进程阻断应用卸载`。类型为`feat`、`fix`、`docs`、`test`、`refactor`或`chore`。
4. 按文件明确暂存，检查`git diff --cached --stat`及实际内容，再提交。源码、测试、必要配置及对应文档一起进入提交；禁止提交凭据、个人扫描内容、构建产物和本机应用包。现有`output/`、`release/`、`.env*`、`node_modules/`、`dist/`、Rust target等保持忽略。
5. 提交后检查工作区。禁止把未跟踪的新模块留在本机、只提交调用方；禁止将“已打包”当成“源码已提交”。不要为补造历史把当前文件拆成并不存在的历史版本。

## 验证与合入

- 功能或执行逻辑改动运行相关专项检查；交付基线运行`npm run check`。界面改动按范围运行浏览器模拟；涉及系统权限、原生窗口、废纸篓的场景另做原生验收。记录失败、跳过及未运行项，不用模拟替代系统验收。
- 仅文档改动检查链接、编号及事实，无需重复应用构建。重建交付包后必须运行完整包签名核验；签名有效不等于系统已授权。
- 本地验收通过、工作区干净后，使用快进合入，避免无意义合并提交：

  ```bash
  git switch main
  git merge --ff-only feat/application-details
  ```

  无法快进时先检查分叉原因并制定合并方案，不自动重写共享历史。禁止`reset --hard`、`clean -fd`、移动已有版本标签或强推作为日常解决办法。
- 远端协作使用PR（合并请求），填写仓库模板并等待现有macOS检查。合并远端PR与推送属于外部写入，须获得相应授权。本地快进不代表远端已更新。
- 仓库本地设置`pull.ff=only`、`push.default=simple`；只影响本仓库，不修改全局Git配置。它们不拦截直接提交`main`，也不等于GitHub分支保护。

## 版本与标签

- 应用版本为`主版本.次版本.修订版本`：修复及兼容优化通常增加修订号；不兼容变化或大阶段调整再评估主／次版本。仅文档、验收补证和分支整理不升级应用。
- 应用升级同步`package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`、`src-tauri/tauri.conf.json`。README及日志的“当前交付版本”仅在实际完成本地交付后更新，预览与未交付源码须单列。
- 一个已提交、已验证的交付源码对应一个附注标签`v<版本>`。标签说明包含交付范围、验证摘要、已知限制与修改记录编号；标签不会证明已公证、已发布或权限验收完整。
- 标签必须指向包含该版本源码的提交，创建前核对五处版本及工作区状态。例如：

  ```bash
  git status --short
  git tag -a v0.9.32 -F /tmp/disk-care-version-note.txt main
  git show --no-patch v0.9.32
  ```

  示例说明文件需事先写好，不能仅凭版本字符串自动打标。同版本后续仅文档补证可进入新提交，已有标签不移动；功能修复需新版本。
- 不改变产品行为的测试运行器、CI和开发工具补丁可单独提交，不升级现有应用或移动原交付标签；应注明固定包未以新工具重建，不能冒充新包交付。
- 已有应用包备份保留原策略；源码标签不能代替签名验证或应用备份。若需回退，先说明数据和签名影响，使用新提交恢复源码，不擅自移动共享分支或标签。
- 只有需要同时维护多个交付系列时才增加`release/<系列>`，目前不建立。
